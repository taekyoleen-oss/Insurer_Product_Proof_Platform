# IPPP 적정성 진단 · 벤치마킹 · 개선 로드맵 (v1)

> 작성일: 2026-06-07 · 대상: `Insurer_Product Proof Platform` (설계서 v1.3 기준)
> 범위: 도메인 워크플로 정확성 · 보안/RLS/권한 · 모니터링 UX · 성능/접근성/품질 (4개 축 동일 가중)
> 방법: 설계서(`docs/IPPP_design_spec_v1.2.md`)의 **의도**와 실제 구현 코드의 **현실**을 대조하고,
> 유사 도메인 베스트프랙티스와 비교하여 적정성·격차를 도출.

## 0. 한눈에 보기 (Executive Summary)

IPPP는 **보험사 ↔ 계리법인 간 위험률·보험료 검증 협업 포털**로, 사실상 회계감사 업계의
**PBC(Prepared-By-Client) 요청관리 포털**과 **모델검증 거버넌스 도구**의 교집합에 위치한다.
도메인 적합도가 높고(역할 4계층, 검증 건 상태머신, 기관별 실적 리포트), UI 완성도도 양호하다.

그러나 진단 결과 **운영 스키마와 형상관리(VCS) 마이그레이션이 서로 다른 "스키마 드리프트"**가
구조적으로 존재하며, 이로 인해 **신규 환경(=하네스/재배포)에서 핵심 기능이 즉시 깨지는** 상태다.
또한 검증 도메인의 핵심인 **(a) 독립 검증확인서 기반 완료 통제**와 **(b) 권한 회수(비활성화)의 RLS 일관성**,
**(c) 감사 추적(audit trail)** 이 미흡하다.

| 축 | 적정성 | 핵심 결론 |
|----|--------|-----------|
| 도메인 워크플로 정확성 | ▲ 보통 | 상태머신·리포트는 우수하나, **2단계 완료 통제가 우회 가능**. 감사 추적 부재. |
| 보안 · RLS · 권한 | ▲ 보통 | RLS 골격은 견고하나 **`is_admin()`이 `is_active`를 무시** → 권한 회수 후에도 DB 접근. 초대 수락이 **브라우저에서 권한 테이블 직접 INSERT**. |
| 모니터링 UX | ● 양호 | KPI·차트·기관 리포트 충실. **연체(overdue) 가시성**과 활동 타임라인 보강 여지. |
| 성능 · 접근성 · 품질 | ● 양호 | 타입체크 통과, 인덱스 적정. **자동화 테스트 0건**, 스토리지 정책이 코드에 없음. |

## 1. 유사 앱 벤치마킹

IPPP와 기능이 겹치는 4개 제품군과 대조한다.

| 제품군 | 대표 제품 | IPPP와의 공통점 | IPPP가 차용할 베스트프랙티스 |
|--------|-----------|------------------|------------------------------|
| **감사 PBC/요청관리 포털** | Suralink, AuditDashboard, Inflo | 의뢰자↔수행기관 자료 교환, 요청 단위 상태(미제출/수령/승인), 마감일, 코멘트 스레드, 대시보드 | ① **요청 내 항목별 체크리스트**(건 하위 deliverable 단위 상태) ② **"수령 vs 승인" 분리** 상태 ③ **연체 자동 강조·리마인더** |
| **GRC/감사관리** | AuditBoard, Workiva, Diligent | 워크플로 상태 전이, 역할 기반 접근, 리포팅, 사인오프 | ④ **불변 감사 로그**(누가·언제·무엇을 조회/다운로드/상태변경) ⑤ **직무 분리(SoD)와 사인오프 무결성** |
| **모델검증 거버넌스** | Moody's AXIS, FIS Prophet, Milliman 워크플로 | 위험률·보험료 산출물의 독립 검증, 버전 관리, 검증 의견서 | ⑥ **검증 산출물 버전 추적**(IPPP 이미 보유) ⑦ **독립성 통제**: 검증확인서는 반드시 외부기관이 발행 |
| **보안 파일 교환(VDR)** | Datasite, Intralinks, iDeals | 권한별 접근, 만료 링크, 감사 로그 | ⑧ **만료 링크**(IPPP 24h Signed URL 보유) ⑨ **접근 로그·워터마킹** ⑩ **세밀한 최소권한** |

### 1.1 벤치마킹 종합 결론

- IPPP의 포지셔닝은 **"actuarial PBC 포털"** 로 명확하며, 핵심 골격(역할 계층·상태머신·기관 리포트)은
  동급 SaaS와 견주어 **경쟁력 있는 출발점**이다. 특히 **기관별 실적(완료율·평균 소요일) 리포트**는
  단순 포털 대비 앞선 기능이다.
- 반면 규제 인접 도메인(K-ICS/IFRS17 검증)에서 필수인 **감사 추적**과 **독립성·직무분리 통제**,
  그리고 **권한 회수의 즉시성**은 동급 제품 대비 미흡하다. 아래 개선안의 우선순위 근거가 된다.

## 2. 진단 — 발견 사항 (우선순위별)

심각도: **P0**(데이터/보안/기능 파손) · **P1**(도메인 정합성·신뢰성) · **P2**(품질·UX).
각 항목은 근거 파일·라인과 권고를 포함한다.

### P0 — 즉시 수정 (배포/재현 불가 또는 보안 구멍)

| # | 발견 | 근거 | 영향 |
|---|------|------|------|
| **P0-1** | **스키마 드리프트: `ippp_invitations.used_at` vs 코드 `accepted_at`** | 마이그레이션은 `used_at`(L114) 생성, 코드는 전부 `accepted_at` 사용(`api/invitations/route.ts:69`, `auth/invite/page.tsx:37,105`, `lib/actions/invitations.ts:87`, `types/index.ts:145`) | 깨끗한 DB에서 **초대 조회/수락 전부 실패**(컬럼 없음). 운영은 수동 변경으로 추정 → VCS≠운영. |
| **P0-2** | **`createRequest`가 `NOT NULL` 배열에 `null` 삽입** | `lib/actions/requests.ts:59,62` (`assigned_member_ids ?? null`, `hazard_type ?? null`); 컬럼은 `NOT NULL DEFAULT '{}'` (migration L64,66). 폼은 `assigned_member_ids`를 보내지 않음 | 깨끗한 DB에서 **검증 건 생성이 항상 실패**. 운영이 동작 = 컬럼이 nullable로 드리프트됨을 시사. |
| **P0-3** | **권한 회수(비활성화) 후에도 RLS 접근 유지** | `is_admin()`(migration L219-225)과 `get_my_internal_role()`(L200-206)가 `is_active`를 확인하지 않음. 미들웨어·`requireAdmin()`은 확인하나 RLS는 우회됨 | 비활성화된 내부관리자가 **여전히 모든 테이블 SELECT/UPDATE 가능**. 권한 회수 무력화. |
| **P0-4** | **초대 수락이 브라우저 anon 클라이언트로 권한 테이블 직접 INSERT** | `auth/invite/page.tsx:86-100`이 `ippp_agency_members`/`ippp_internal_members`에 클라이언트에서 INSERT. 해당 INSERT는 `is_admin()`/`agency_admin`만 허용(RLS) → 신규 가입자는 통과 불가 | 초대 수락 **RLS로 차단**(정상 동작 불가) 또는 정책이 느슨하면 **자기 권한 상승** 위험. 서버(서비스롤) 처리로 이전 필요. |
| **P0-5** | **Storage 버킷·정책이 형상관리에 없음** | 마이그레이션에 `ippp-files` 버킷 생성/Storage RLS 없음. 코드만 `storage.from('ippp-files')` 사용 | 신규/로컬 환경에서 **업로드·다운로드 전부 실패**. 인프라가 코드화되지 않음. |

### P1 — 도메인 정합성 · 신뢰성

| # | 발견 | 근거 | 영향 |
|---|------|------|------|
| **P1-1** | **2단계 완료 통제 우회 가능** | `completeRequest`는 "삭제되지 않은 파일 ≥1"만 검사(`lib/actions/requests.ts:150-159`), 업로더가 **기관인지 확인 안 함**. `RequestStatusActions`도 `hasFile`만 검사 | 설계 §1.3/§5: "기관이 **검증확인서** 업로드 → admin 승인". 실제로는 **admin 첨부 파일만으로 완료** 가능 → 독립 검증 통제 무력화. |
| **P1-2** | **감사 추적(audit trail) 부재** | 상태 변경·파일 다운로드(Signed URL 발급)·열람 이력을 저장하는 테이블 없음. `ippp_notifications`는 이메일 로그일 뿐 | 규제 인접 검증 업무에서 **"누가 언제 무엇을" 추적 불가**. 분쟁/감리 대응 취약. |
| **P1-3** | **`assignAgency`가 `assigned_member_ids`를 `null`로 설정** | `lib/actions/requests.ts:188` `assigned_member_ids: null`; 컬럼 `NOT NULL` | 기관 재배정 시 **에러**(클린 스키마) 또는 알림 대상 소실. |
| **P1-4** | **재초대 가드가 잘못된 컬럼 참조** | `lib/actions/invitations.ts:87` `existing.accepted_at`(존재 안 함 → undefined) → "이미 수락" 검사 무력 | 수락된 초대도 재초대 통과. P0-1과 동근원. |
| **P1-5** | **마감 임박 KPI가 연체 건을 제외** | `due_date >= today` 조건(`queries/requests.ts:166,288` 등) | 이미 **마감 지난 미완료 건**이 "임박/위험"에서 빠져 모니터링 사각지대. 설계 의도(시각 경고)와도 불일치. |

### P2 — 품질 · UX · 운영

| # | 발견 | 근거 / 권고 |
|---|------|-------------|
| **P2-1** | **자동화 테스트 0건** | 테스트 프레임워크·CI 없음. 본 작업에서 하네스로 보강. |
| **P2-2** | **순수 도메인 로직이 서버 모듈에 결합** | 상태전이·기간계산·경로빌더가 `'use server'`/쿼리 파일에 내장 → 단위 테스트 불가. `lib/domain/`로 추출 권고(본 작업 반영). |
| **P2-3** | **서버 액션이 자기 API로 fetch 왕복** | `comments.ts:59`, `invitations.ts:46` → 같은 프로세스 내 HTTP 왕복. 직접 함수 호출이 견고. |
| **P2-4** | **파일 개수 상한(15)·MIME 미검증** | `files.ts`는 100MB만 검사. 설계 §1.5 상한 미구현. |
| **P2-5** | **`Request.agency_id` 타입이 non-null** | `types/index.ts:93` `string`이나 DB는 `ON DELETE SET NULL`로 nullable. 타입 정확성 보강. |
| **P2-6** | **`.single()` 남용** | 무결과시 에러 코드(PGRST116) 의존. `.maybeSingle()`이 의도 명확. |

## 3. 개선 로드맵

### 3.1 본 세션에서 추진 (자율 실행)

1. **정정 마이그레이션** (`supabase/migrations/*_hardening.sql`) — 멱등 작성
   - `used_at` → `accepted_at` 정규화 (P0-1, P1-4)
   - 배열 컬럼 `NOT NULL DEFAULT '{}'` 보강 + 기존 NULL 백필 (P0-2, P1-3)
   - `is_admin()`·`get_my_internal_role()`에 `is_active` 반영 (P0-3)
   - `ippp-files` 버킷 + Storage RLS 정책 코드화 (P0-5)
   - 감사 로그 테이블 `ippp_audit_logs` 신설 + RLS (P1-2 기반)
2. **코드 수정**
   - `createRequest`/`assignAgency` 배열 NULL 제거 (P0-2, P1-3)
   - `completeRequest` — **기관(외부) 업로더의 미삭제 파일 ≥1** 을 완료 전제로 강화 (P1-1)
   - 초대 수락 **서버 라우트(`/api/invitations/accept`, 서비스롤)** 로 이전 (P0-4)
   - 마감 임박/연체 분리 노출 (P1-5)
   - 순수 로직 `lib/domain/`로 추출 (P2-2)
3. **테스트 하네스** (`harness/`)
   - 즉시 실행 가능한 **순수 로직 회귀 테스트**(node:test, 의존성 0)
   - **격리 DB 통합 하네스**(`.env.harness`, 운영 URL 차단 가드, 시드+RLS/플로 검증)
   - 발견 오류 수정 후 재실행

### 3.2 차기(v1.4+) 권고 — 벤치마킹 반영

- 요청 하위 **항목 체크리스트**와 "수령/승인" 분리 상태 (Suralink/AuditDashboard)
- **연체 SLA 대시보드 + 자동 리마인더 다이제스트**
- 다운로드/열람 포함 **활동 타임라인 UI**(`ippp_audit_logs` 기반)
- 파일 **워터마킹·열람 추적**, 보존/법적보류(retention/legal hold) 정책

## 4. 적정성 결론

IPPP는 도메인 적합성과 UI 완성도 측면에서 **실사용 가능한 수준의 골격**을 갖추었고,
기관 실적 리포트 등 일부 기능은 동급 포털보다 앞선다. 다만 **신규 환경 재현성(스키마 드리프트)**,
**독립 검증 통제·권한 회수의 RLS 일관성**, **감사 추적**이라는 규제 인접 도메인의 핵심 요건에서
즉시 보완이 필요하다. 본 문서의 P0/P1 항목을 본 세션에서 코드·스키마·하네스로 추진한다.

> 진행 경과·검증 결과는 `docs/IPPP_harness_report.md`에 누적 기록한다.
